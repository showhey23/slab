エージェント型アーキテクチャとオーケストレーションAGENTIC ARCHITECTURE & ORCHESTRATION

GOAL
Claude が自律的にタスクを遂行する「エージェント型ループ」の制御フローを、stop_reason を唯一の信号として正しく回せるようになる。さらに、1体のエージェントで足りない複雑な仕事を、コーディネーターが専門サブエージェントへ委任するハブ・アンド・スポーク型に分解し、コンテキストの明示的受け渡し・並列スポーン・フックによる決定論的強制・セッションの再開／フォークまでを場面に応じて設計できるようになる。本ドメインは試験で最大の27%を占める土台であり、「ループはどう終わるか」「サブエージェントは何を受け取るか」「保証が要る統制はプロンプトかフックか」を場面から選ばせる設問が中心になる。
01

ループの主はモデルではなく stop_reason。 Claude にリクエスト→stop_reason を検査→"tool_use" ならツールを実行して結果を会話履歴に追記し再送、"end_turn" なら終了。自然言語の合図やアシスタント文の有無で終了判定するのはアンチパターン。

02

サブエージェントは“記憶を継承しない”。 Task ツールで起動されたサブエージェントは独立コンテキスト（独自のシステムプロンプト・ツール・コンテキストウィンドウ）で動く。親の会話は見えず、渡るのはプロンプトに明示した内容だけ、返るのは最終テキストだけ。

03

保証が要るならフック、可変でよければプロンプト。 本人確認→返金のように決定論的遵守が必須なら、プロンプト指示（失敗率ゼロでない）ではなくプログラム的な前提条件ゲートやフックで物理的にブロックする。

04

コーディネーターは“狭く割りすぎる”と漏れる。 「創造産業」を視覚芸術だけに分解すると音楽・執筆・映画が抜ける。タスク分解の広さこそコーディネーターの責任で、下流のサブエージェントは割り当てられた範囲を正しくこなしているだけ。

05

並列は1応答で複数 Task を発行。 別ターンに分けず、1回のコーディネーター応答内で複数の Task 呼び出しを出すと並列実行になる。再開は --resume、分岐探索は fork_session。

AGENTIC LOOP

1.1 自律タスク実行のためのエージェント型ループ

エージェント型ループのライフサイクルは「送信→stop_reason 検査→ツール実行→結果を会話履歴へ追記→再送」の反復。継続/終了の判断は stop_reason という権威的な信号のみで行い、モデル主導の意思決定（次に呼ぶツールを文脈から推論）と、事前固定の決定木やツール列とを区別することが問われる。

図：エージェント型ループのライフサイクル

制御フローの実装Loop control flow

stop_reason=="tool_use" の間は継続し、"end_turn" で終了。ツール結果は反復の間に会話コンテキストへ追記し、新情報をモデルの推論へ取り込ませる。

詳説ツール結果を会話履歴に積むことで、モデルは次のアクションを文脈から推論できる。これがモデル主導（適応的）と、事前構成の決定木との決定的な違い。
アンチパターン①自然言語の合図を解析して終了判定／②恣意的な反復上限を主要な停止機構にする／③アシスタントのテキスト有無を完了指標にする——いずれも不可。

モデル主導 vs 事前構成Model-driven vs pre-configured

どのツールを次に呼ぶかを Claude が文脈から推論するのがモデル主導。固定のツール列・決定木は柔軟性を欠く。

使い分けタスクが多様・曖昧ならモデル主導が強い。逆に厳密な順序保証が要る箇所は1.4のフック/前提条件で“外側から”縛る。
試験「ループの終了をどう判定するか」は stop_reason 一択。テキスト解析・反復上限・文有無はすべてディストラクター。

MULTI-AGENT

1.2 コーディネーター・サブエージェントの統制

ハブ・アンド・スポーク型では、コーディネーターが全サブエージェント間の通信・エラー処理・情報ルーティングを一手に管理する。サブエージェントは分離コンテキストで動き、コーディネーターの会話履歴を自動継承しない。コーディネーターの責務はタスク分解・委任・結果集約・どのサブエージェントを呼ぶかの判断にある。

ハブ・アンド・スポークHub-and-spoke

全通信をコーディネーター経由でルーティングし、可観測性・一貫したエラー処理・制御された情報フローを得る。

詳説常に全パイプラインを通すのではなく、クエリの要件を分析して呼ぶサブエージェントを動的選択する。範囲はサブエージェント間で分割し重複を最小化（異なるサブトピック／ソース種別を割当）。
反復改善統合出力のギャップを評価→対象を絞ったクエリで検索・分析へ再委任→カバレッジが十分になるまで統合を再呼び出し。

狭すぎる分解の罠Narrow decomposition

広範なトピックを過度に狭く分解すると、サブエージェントが正しく動いても全体のカバレッジが欠落する。

ひっかけ「創造産業」を視覚芸術（デジタルアート/グラフィック/写真）だけに割ると音楽・執筆・映画が抜ける。原因はコーディネーターの割当で、下流のエージェントを責めるのは誤り。
試験症状（最終レポートの抜け）→ログ（分解内容）→根本原因（分解が狭い）の因果を読ませる。

SPAWN & CONTEXT

1.3 サブエージェントの呼び出し・コンテキスト・スポーン

サブエージェントを起動する仕組みが Task ツール。コーディネーターが呼び出すには allowedTools に "Task" を含める必要がある。サブエージェントは親コンテキストを自動継承せず、メモリも共有しないため、必要な内容はプロンプトに明示して渡す。

明示的コンテキスト受け渡しExplicit context passing

先行エージェントの完全な調査結果をサブエージェントのプロンプトに直接含める（例：Web検索結果と文書分析の出力を統合サブエージェントに渡す）。

詳説出典を保つため、構造化データ形式でコンテンツとメタデータ（ソースURL・文書名・ページ番号）を分離して渡す。AgentDefinition で各タイプの説明・システムプロンプト・ツール制限を構成。
スキルコーディネーターのプロンプトは手続き的な手順ではなく、リサーチ目標と品質基準を指定して適応性を持たせる。

並列スポーンParallel spawn

別々のターンに分けず、1回のコーディネーター応答内で複数の Task 呼び出しを発行すると並列実行になりレイテンシが下がる。

フォーク共有の分析ベースラインから分岐アプローチを探索するにはフォークベースのセッション管理（fork_session）。
試験「並列化の正しい実装」は“同一応答で複数 Task”。allowedTools に Task が無ければ起動不可。

ENFORCEMENT & HANDOFF

1.4 強制と引き継ぎのパターン

ワークフローの順序付けには、プログラム的強制（フック・前提条件ゲート）とプロンプトベースの誘導がある。決定論的遵守が必須な場面（例：金融操作前の本人確認）では、プロンプト指示だけでは失敗率がゼロでない。プロセス途中のエスカレーションには、顧客詳細・根本原因・推奨アクションを含む構造化引き継ぎを用いる。

前提条件ゲートProgrammatic prerequisites

前提ステップ完了まで下流ツール呼び出しをブロック（例：get_customer が検証済み顧客IDを返すまで process_refund を阻止）。

詳説複数懸案のリクエストは個別項目に分解し、共有コンテキストで並行調査してから統一解決へ統合する。
試験「12%でget_customerをスキップ」問題の正解は、プロンプト強化や few-shot ではなくプログラム的前提条件。金銭被害が出る統制は決定論で。

構造化引き継ぎStructured handoff

会話トランスクリプトを見られない人間エージェントへ渡す要約（顧客ID・根本原因・返金額・推奨アクション）。

詳説人間が文脈ゼロから再調査せずに済むよう、必要な事実を構造化して集約する。
実装例返金限度超過はフックでブロックし、エスカレーション用の構造化サマリーへリダイレクト。

1.5 フックによるツール呼び出し傍受とデータ正規化

フックはエージェント実行中のイベントで発火する。PostToolUse はツール結果をモデルが処理する前に変換（正規化）でき、発信されるツール呼び出しを傍受する種類はコンプライアンスルールを強制できる。鍵は「決定論的保証＝フック」「確率的遵守＝プロンプト指示」という対比。

PostToolUse 正規化Normalize tool output

異なる MCP ツール由来の異種フォーマット（Unixタイムスタンプ・ISO 8601・数値ステータスコード）を、エージェント処理前に統一形式へ正規化する。

詳説PostToolUse はモデルが結果を見る前に出力を書き換えられる。組み込み/ MCP どちらのツールにも適用可能。
試験「異種データの整え方」＝PostToolUseで正規化。PreToolUse は実行前に呼び出しをブロック/改変できる点も押さえる。

ポリシー強制の傍受Policy interception

閾値超の操作（例：$500超の返金）をブロックし、代替ワークフロー（人間へのエスカレーション）へリダイレクト。

使い分けビジネスルールが“保証された遵守”を要求するなら、プロンプトベース強制ではなくフックを選ぶ。
実装例返金額・操作種別を検査し、違反時はツール実行を未然に止める。

HOW TO STUDY

「ループ→委任→統制→状態」の一筋で覚える

ドメイン1は出題比率が最大（27%）で範囲も広いが、「単体の自律ループ（stop_reason） → 多エージェント委任（コーディネーター/サブエージェント） → 決定論的統制（フック・前提条件） → 状態管理（再開・フォーク）」の4段で束ねると整理しやすい。最頻出は3点で、いずれも“場面から1つ選ぶ”形で問われる――①ループの終了は stop_reason 一択、②保証が要る統制はフック（プロンプトではない）、③サブエージェントは記憶を継承せずプロンプトで明示。混同ペア（PreToolUse/PostToolUse、並列/逐次、再開/新規＋要約）は対で覚えると取りこぼさない。固有のフラグ名・SDK仕様は公式ドキュメントで最終確認すること。

ツール設計と MCP 統合TOOL DESIGN & MCP INTEGRATION

GOAL
エージェントが正しい道具を正しく選べるよう、ツールの説明（description）と境界を設計し、失敗を構造化エラーで語らせ、役割に応じてツールを配分し tool_choice を構成できるようになる。MCP サーバーをプロジェクト/ユーザースコープで統合し、リソースでカタログを公開して探索的呼び出しを減らす。組み込みツール（Read/Write/Edit/Bash/Grep/Glob）の使い分けまでを含む。出題比率は18%。
01

ツールの説明＝LLM の選択メカニズム。 説明が最小限だと類似ツールの選択が不安定になる。入力形式・クエリ例・エッジケース・「いつ使うか」の境界を書き、重複は改名/分割で解消する。

02

失敗は“構造化”して伝える。 画一的な「Operation failed」では回復判断ができない。errorCategory（transient/validation/permission）・isRetryable・人間可読な説明を返す。MCP では isError フラグで失敗を伝える。

03

4
STRUCTURED ERRORS

2.2 MCP ツールの構造化エラー

MCP は isError フラグで失敗をエージェントへ伝える。一時的エラー（タイムアウト/利用不可）・検証エラー（無効入力）・ビジネスエラー（ポリシー違反）・権限エラーを区別し、再試行可否を構造化メタデータで示すことで無駄な再試行を防ぐ。

表：エラー種別と扱い
種別例再試行返すべき情報
一時的(transient)タイムアウト・サービス利用不可可isRetryable=true。ローカル回復を試行
検証(validation)無効な入力不可何が無効か（人間可読）
ビジネス(business)ポリシー違反（限度超返金）不可retriable:false ＋顧客向け説明
権限(permission)アクセス不可要判断アクセス失敗か空結果かを区別

構造化メタデータStructured metadata

errorCategory（transient/validation/permission）・isRetryable ブール・人間可読な説明を返す。

詳説サブエージェントは一時障害をローカル回復し、解決不能なものだけ部分結果・試行内容とともにコーディネーターへ伝播する。
試験「Operation failed」では回復判断不可。アクセス失敗（再試行判断要）と有効な空結果（一致なしの成功）を取り違えない。

ビジネスエラーの伝え方Business errors

ポリシー違反は retriable:false と顧客にわかりやすい説明を付け、エージェントが適切に応対できるようにする。

実装例限度超の返金は再試行不要であることを明示し、エスカレーションへ誘導。

2.4 MCP サーバーの統合

MCP のスコープは、共有チームツール向けのプロジェクトレベル（.mcp.json）と、個人/実験向けのユーザーレベル（~/.claude.json）。.mcp.json では環境変数展開（例 ${GITHUB_TOKEN}）でシークレットをコミットせず認証情報を扱える。構成済み全サーバーのツールは接続時に検出され、同時に利用可能。

プロンプトエンジニアリングと構造化出力PROMPT ENGINEERING & STRUCTURED OUTPUT

GOAL
「曖昧な指示」を「明示的な基準」に変えて精度を上げ誤検知を減らし、few-shot で出力を一貫させ、tool_use ＋ JSON スキーマで確実に構造化出力を得る。検証・再試行・フィードバックループで抽出品質を守り、Message Batches API でコスト効率よく大量処理し、独立インスタンスやマルチパスでレビュー品質を高める。出題比率は20%。
01

「保守的に」では精度は上がらない。 「コメントが正確か確認」より「主張された挙動が実コードと矛盾する場合のみフラグ」のように明示的・カテゴリ別の基準を書く。誤検知の多いカテゴリは正確なカテゴリへの信頼まで損なう。

02

詳細指示で揃わないなら few-shot。 2〜4個の対象を絞った例で、なぜその行動を選んだかの推論や望ましい出力形式（場所・問題・重大度・修正案）を示す。新規パターンへの一般化と抽出のハルシネーション低減に効く。

03

確実な構造化は tool_use ＋ JSON スキーマ。 構文エラーは消えるが意味エラー（合計不一致・フィールド誤配置）は防げない。情報が無いかもしれないフィールドは nullable にし、必須充足のための値の捏造を防ぐ。

04

再試行は“形式/構造の誤り”には効くが、情報が無い時は無力。 元文書・失敗した抽出・具体的な検証エラーを付けて自己修正させる。情報が外部文書にしか無い場合の再試行は無駄。

05

Batches API は 50%引き・最大24時間・SLA保証なし。 ブロッキングなマージ前チェックには不可、夜間/週次の非ブロッキング処理に最適。単一リクエスト内のマルチターンのツール呼び出しは非対応。custom_id で対応付け。

EXPLICIT CRITERIA

4.1 明示的基準で精度を上げ誤検知を減らす

曖昧な指示より明示的基準。「保守的に」「高信頼度の所見のみ報告」のような一般指示は、具体的なカテゴリ別基準ほど精度を上げない。誤検知率は開発者の信頼に直結し、誤検知の多いカテゴリが正確なカテゴリへの信頼まで損なう。

報告/スキップの基準Report vs skip

信頼度ベースのフィルタに頼らず、報告する問題（バグ・セキュリティ）とスキップ（軽微スタイル・ローカルパターン）を定義。各重大度に具体的コード例を付け一貫分類。

詳説誤検知の多いカテゴリは一時的に無効化し、そのカテゴリのプロンプトを改善する間に開発者の信頼を回復する。
試験「be conservative」「only high-confidence」は精度を上げない。具体的・カテゴリ別の基準が正解。

4.2 few-shot プロンプティング

詳細な指示だけでは一貫しない時、few-shot 例が最も効果的。曖昧ケースの扱い方を示し、事前指定ケースだけに一致させるのでなく判断を新規パターンへ一般化させる。抽出タスクのハルシネーション低減にも効く。

2〜4個の対象を絞った例で、もっともらしい代替よりなぜその行動かの推論を示す。望ましい出力形式（場所・問題・重大度・修正案）も例で固定。

4.3 tool_use と JSON スキーマで構造化出力

tool_use（JSON スキーマ）はスキーマ準拠の構造化出力を保証する最も信頼できる手法で、JSON 構文エラーを排除する。ただし意味エラー（明細が合計に一致しない・値が誤フィールド）は防げない。

表：tool_choice と用途
設定意味使う場面
"auto"ツールを呼ばずテキスト可自由応答も許す
"any"必ずツール（どれかは選択）複数抽出スキーマ・文書型不明でも構造化保証

スキーマ設計Schema design

抽出ツールを JSON スキーマで定義し tool_use 応答から構造化データを取り出す。情報が無い可能性のあるフィールドは nullable にし値の捏造を防ぐ。

詳説曖昧ケースに "unclear" の enum、拡張分類に "other"＋詳細フィールド。書式正規化ルールをプロンプトに併記。

構文 vs 意味Syntax vs semantics

厳格スキーマは構文エラーを消すが、合計不一致や誤配置などの意味エラーは別途検証が要る（→4.4）。

試験「必ず構造化」＝"any"、「特定を先に」＝強制。nullable で捏造防止。

4.5 効率的なバッチ処理戦略

Message Batches API＝50%コスト削減・最大24時間の処理ウィンドウ・保証レイテンシSLAなし。非ブロッキングでレイテンシ寛容な処理（夜間レポート・週次監査・夜間テスト生成）に適し、ブロッキング（マージ前チェック）には不適。単一リクエスト内のマルチターンのツール呼び出しは非対応。custom_id で対応付け。

API の使い分けと失敗処理Batch strategy

ブロッキングなマージ前チェックは同期 API、夜間/週次分析はバッチ API。SLA 制約からバッチ送信頻度を計算（24時間処理で30時間SLAを保証する4時間ウィンドウ等）。

詳説失敗は custom_id で特定し、失敗文書のみ修正（コンテキスト超過はチャンク化）して再送。大量処理前にサンプルでプロンプト改善し初回成功率を上げる。
試験「マージ前チェックもバッチへ」は誤り（24h・SLAなし）。バッチ結果は custom_id で対応付くため順序問題は誤解。

4.6 マルチインスタンス／マルチパスのレビュー

自己レビューはモデルが生成時の推論文脈を保持し、自身の決定を疑いにくい。独立レビューインスタンス（推論文脈なし）は自己レビュー指示や拡張思考より微妙な問題を捉える。大規模レビューはファイルごとのローカル分析＋ファイル横断統合に分け、注意の希薄化と矛盾所見を避ける。

JSON 構文エラーは消えるが、意味エラー（明細が合計に一致しない・値が誤フィールド）は残る（→検証で対処）。情報が無いかもしれないフィールドは nullable にして、必須充足のための値の捏造を防ぐ。
Q4抽出の再試行はどんな時に成功し、どんな時に無駄か。
書式の不一致や構造的な出力エラーには成功（元文書・失敗抽出・具体的検証エラーを付けて自己修正）。必要情報が提供されていない外部文書にしか存在しない場合は無駄。
Q5マージ前チェックと夜間レポートの両方を Message Batches API に切り替える提案。どう評価するか。
夜間レポートのみバッチ、マージ前チェックは同期 API のまま。バッチは50%削減だが最大24時間・SLA保証なしでブロッキング処理に不適。「順序問題で両方同期」は誤解（custom_id で対応付く）、タイムアウトフォールバックは過剰。
Q614ファイルの一括レビューが、矛盾・見落とし・深さのムラを起こす。どう再構築するか。なぜ大窓モデルでは不十分か。
焦点を絞ったパスに分割：各ファイルを個別にローカル分析→別個のファイル横断統合パス。根本原因は注意の希薄化で、コンテキスト窓を大きくしても注意の質は解決しない。3回中2回一致のみ採用は本物のバグ検出を抑制してしまう。

コンテキスト管理と信頼性CONTEXT MANAGEMENT & RELIABILITY

GOAL
長い対話・大規模探索・多源統合でも壊れない信頼性を設計できるようになる。重要な事実を要約に溶かさずケース事実ブロックとして保持し、lost in the middle を意識した配置で位置効果を緩和する。適切なエスカレーション基準、マルチエージェントの構造化エラー伝播、スクラッチパッドやマニフェストでのクラッシュ回復、信頼度較正と人間レビューのルーティング、そして主張とソースの対応付けによる出所保持までを扱う。出題比率は15%。
01

数字を要約で溶かさない。 段階的要約は金額・割合・日付・顧客が述べた期待を曖昧にしがち。取引上の事実は要約履歴の外の「ケース事実」ブロックとして各プロンプトに含める。

02

中間は読み落とされる（lost in the middle）。 長い入力は先頭と末尾が確実に処理され中間が抜ける。重要所見の要約を先頭に置き、明示的なセクションヘッダーで整理して位置効果を緩和する。

5.1 長い対話で重要情報を保持

ケース事実ブロックCase facts block

取引上の事実（金額・日付・注文番号・ステータス）を抽出し、要約履歴の外の永続ブロックとして各プロンプトに含める。多問題セッションは別レイヤーに構造化。

ESCALATION

5.2 エスカレーションと曖昧性解消

適切なエスカレーショントリガーは、①顧客が人間を要求、②ポリシーの例外/欠落（複雑なだけではない）、③有意義な進展ができない。感情ベースや自己申告の信頼度スコアは、実際のケース複雑さの信頼できない代理指標。

基準ベースの判断Criteria-based

明示的なエスカレーション基準＋few-shot 例で、いつエスカレーションし、いつ自律解決するかを示す。人間要求には調査を試みず即応。

詳説問題が能力範囲内なら不満を認めつつ解決を申し出て、顧客が希望を繰り返した時のみエスカレーション。
ひっかけ感情分析や自己申告信頼度でのエスカレーションは不可。感情はケース複雑さと相関しない。

曖昧性の解消Ambiguity resolution

ツール結果が複数一致を返したら、ヒューリスティック選択でなく追加識別子を求める。ポリシーが沈黙/曖昧な要求（自社サイトのみ規定での競合価格マッチング等）はエスカレーション。

試験55%解決で単純ケースをエスカレーションし複雑を抱える＝明示基準＋few-shotが第一手。分類器/感情分析は過剰/誤り。

5.3 マルチエージェントのエラー伝播

5.4 大規模コードベース探索のコンテキスト管理

5.5 人間レビューと信頼度較正

5.6 情報の出所と多源統合の不確実性

主張とソースの対応付けを保持せず要約で圧縮すると出所が失われる。統合エージェントは構造化された主張-ソースマッピングを保持・統合しなければならない。信頼できるソース間で統計が矛盾する場合、任意に1値を選ばず出所付きで注釈する。

GOAL

出題例と解説

本シナリオは公式ガイドにサンプル問題が無いため、対応するタスクステートメント（4.3〜4.5／5.5）と演習3に基づく代表的な設問で解説します。

例1請求書から明細を抽出する。一部のフィールドは文書に存在しないことがある。モデルが必須フィールドを満たすために値を捏造するのを防ぐ最も適切なスキーマ設計は。Extracting line items from invoices, some fields may be absent. Best schema design to prevent the model from fabricating values to satisfy required fields?
A) 全フィールドを必須にして欠落時はエラーMake all fields required and error on absence
B) 存在しない可能性のあるフィールドを nullable（任意）にし、無い場合は null を返させるMake possibly-absent fields nullable and return null when absent
C) プロンプトで「捏造禁止」とだけ指示Just instruct "do not fabricate" in the prompt
D) 抽出後に人手で全件確認Manually verify every extraction afterward

正解: B

情報が無いかもしれないフィールドはnullable（任意）として設計し、無い場合は値を捏造せず null を返させる。必須フィールドを満たそうとする捏造を構造的に防げる。曖昧ケースには "unclear"、拡張分類には "other"＋詳細フィールドを足す。

例2抽出結果の検証が失敗した。再試行が「効く場合」と「無駄な場合」の正しい区別は。Extraction validation failed. Correct distinction between when a retry helps and when it is futile?
A) 常に再試行すれば必ず直るRetrying always fixes it
B) 書式の不一致や構造的な出力エラーは再試行で直るが、必要情報が提供外の文書にしか無い場合は無駄Retry fixes format/structural errors, but is futile when the needed info exists only in an unprovided document
C) 再試行は常に無駄なので人手に回すRetry is always futile, so route to humans
D) スキーマを緩めれば全て解決Loosening the schema solves everything

正解: B

再試行は形式/構造の誤りには有効（元文書・失敗抽出・具体的検証エラーを付けて自己修正）。一方、必要情報がソースに存在しない場合は何度試しても直らない。意味的検証（合計不一致など）はスキーマでは防げないため別途検証する。

例3抽出システムが全体97%の精度。人間レビューを減らして自動化を進めてよいか。最も健全な進め方は。An extraction system has 97% overall accuracy. Is it OK to reduce human review and automate? Most sound approach?
A) 97%なら全件自動化してよいAt 97%, automate everything
B) 高信頼度抽出の層化無作為抽出でエラー率と新規パターンを測り、文書型・フィールド別に精度を分析、低信頼度/曖昧ソースを人間レビューへ振り分けるUse stratified random sampling of high-confidence extractions to measure error rates and novel patterns; analyze accuracy by document type and field; route low-confidence/ambiguous to human review
C) 全件を引き続き人手確認Keep all manual
D) 信頼度の高い順に並べて上位だけ確認Sort by confidence and check only the top

正解: B

集計精度は特定の文書型/フィールドの低性能を覆い隠す。層化無作為抽出でエラー率・新規パターンを測定し、セグメント別に一貫性を確認してから自動化する。フィールドレベル信頼度をラベル付き検証セットで較正し、低信頼度や曖昧/矛盾ソースを人間レビューへ振り分けて限られたレビュー能力に優先順位を付ける。

CLAUDE CODE

C. Claude Code に MCP を追加する（コマンド）

Claude Code（ターミナルのツール）では claude mcp add コマンドで MCP を追加する。下のコマンドはそのままコピーして使える。コマンドに不安があれば手順A・Bだけでも十分活用できる。

基本：リモート（URL）を追加
書式
claude mcp add --transport http <名前> <URL>
例：Notion をつなぐ
claude mcp add --transport http notion \ https://mcp.notion.com/mcp

認証が必要なリモートは、追加後に Claude Code 内で /mcp と打つとログイン（OAuth）できます。トークンを直接渡す場合は --header "Authorization: Bearer ..." を付けます。

手元で動くサーバー（ローカル）
stdio 形式（-- 以降が起動コマンド）
claude mcp add <名前> -- <起動コマンド> # 例： claude mcp add files -- npx @modelcontextprotocol/server-filesystem ~/Documents
鍵などは -e で渡す
claude mcp add my-server \ -e API_KEY=sk-xxxxx \ -- node server.js

--（ダッシュ2つ）から後ろは「サーバーを起動するコマンド」。その手前は Claude 側のオプション（--transport / --env / --scope）です。

表：スコープ（どこに保存して誰が使えるか）
スコープ保存先使える範囲コマンド例
local（既定）~/.claude.json自分だけ・このプロジェクトclaude mcp add ...
project.mcp.jsonチーム共有（gitで配布）--scope project （または -s project）

FAQ

よくある質問

Q1開発経験がありません。コマンドを使わずにツールを足せますか？
はい。手順A（デスクトップ拡張）はクリックだけで完結します。設定 > 拡張機能 > 拡張機能を参照 > Install の流れで、APIキー等は画面の案内に従って入れるだけ。Node.js 等の準備も不要（アプリ内蔵）。
Q2「拡張機能」「コネクター」「MCPサーバー」は何が違いますか？
裏側はどれも同じ MCP の仕組みです。デスクトップでワンクリック導入できるパッケージが拡張機能、URLでつなぐ外部接続がコネクター、Claude Code から見た呼び名がMCPサーバー。役割で言葉が違うだけと考えてOK。
Q3Claude Code で追加した MCP を「自分だけ／チーム全員／全プロジェクト」で使い分けたい。
スコープを指定します。local（既定）＝自分だけ・このフォルダ、project（--scope project）＝.mcp.json に保存しgitでチーム共有、user（--scope user）＝自分の全プロジェクト。優先順位は local > project > user。
Q4追加したのにツールが出てきません。
まず Claude デスクトップを再起動。次に設定でそのツールの必須項目（APIキー等）が埋まっているか、最新版か、（ローカルなら）ファイルパスが実在するかを確認。Claude Code なら claude mcp list で状態を確認できます。
Q5安全面で気をつけることは？
信頼できる提供元だけ接続すること。外部コンテンツを取得するサーバーはプロンプトインジェクションのリスクがあるため、Anthropic レビュー済みの公式ディレクトリや出所が明確なものを優先します。秘密情報は画面案内どおり入力すれば暗号化保管されます。
Q6試験はどこから申し込みますか？費用は？
Anthropic Partner Academy（anthropic-partners.skilljar.com）から登録し、確認メールの案内に従って Pearson VUE アカウントで日程を予約します（受験は Claude Partner Network 加盟組織の所属者に限られます）。費用は1回 $125 USD（Associate は $99、Architect Professional は $175）。パートナー階層により Select・Preferred・Global Premier は 50% オフが自動適用され、Global Premier は 2026-08-31 まで 100% 割引です。受験には Claude Partner Network 加盟組織のパートナーメールアドレスが必要です。60問・120分・監督付きで、720/1000 で合格、有効期限は 12ヶ月です。
